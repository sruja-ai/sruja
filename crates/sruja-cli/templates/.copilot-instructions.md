# GitHub Copilot - Sruja Architecture DSL Instructions

When working with Sruja architecture DSL (`.sruja` files), follow these guidelines.

## Workflow

1. **Generate** architecture DSL based on requirements
2. **Validate** with `sruja lint <file.sruja>`
3. **Fix** any validation errors
4. **Export** to Markdown/Mermaid if needed: `sruja export markdown <file.sruja>`

## File Context

- **Extension:** `.sruja`
- **Validate:** `sruja lint file.sruja`
- **Export:** `sruja export json|markdown|mermaid file.sruja`

## DSL Structure

1. Start with `architecture "[name]"` block (optional, for organizing)
2. Define components (person, system, container, datastore) **before** using them
3. Nest: systems inside architecture, containers/datastores inside systems
4. Relationships after definitions: `source -> target "label"`

## Component Definitions

### Person (External User)
```sruja
person "User" {
  description "End user who interacts with the system"
}
```

### System (Bounded Context)
```sruja
system "User Service" {
  description "User management and authentication service"
  
  container "User API" {
    technology "Node.js"
    description "REST API for user operations"
  }
  
  datastore "User Database" {
    technology "PostgreSQL"
    description "User data storage"
  }
}
```

### Container (Application/Service)
```sruja
container "Web Frontend" {
  technology "React"
  description "User interface for the application"
}
```

### Datastore (Database/Storage)
```sruja
datastore "Cache" {
  technology "Redis"
  description "Session and data cache"
}
```

## Relationships

- Syntax: `source -> target "label"`
- Use **descriptive labels**: "HTTPS", "REST API", "gRPC", "publishes events to"
- Only reference **defined component IDs**

## Multi-Repo Architecture (Microservices)

When the system spans multiple repositories, use **external systems**:

```sruja
// In user-service/architecture.sruja (THIS REPO)
system "User Service" {
  api = container "User API" {
    technology "Node.js"
    description "User management API"
  }
  
  db = datastore "User Database" {
    technology "PostgreSQL"
    description "User data storage"
  }
  
  api -> db "SQL queries"
}

// Declare external systems from other repositories
order_service = external_system "Order Service" {
  description "Order processing service (github.com/org/order-service)"
  metadata {
    location "github.com/org/order-service"
    tags ["external", "microservice"]
  }
}

payment_service = external_system "Payment Service" {
  description "Payment processing service (github.com/org/payment-service)"
  metadata {
    location "github.com/org/payment-service"
    tags ["external", "microservice"]
  }
}

// Reference external systems in relationships
user_service.api -> order_service.api "REST API"
user_service.api -> payment_service.api "gRPC"
```

## Single-Repo Architecture (Monolith)

For a single repository with all components:

```sruja
architecture "E-commerce Platform" {
  user = person "Customer" {
    description "Online shopper"
  }
  
  system "Web Application" {
    frontend = container "Web Frontend" {
      technology "React"
      description "User interface"
    }
    
    backend = container "API Server" {
      technology "Node.js"
      description "REST API server"
    }
    
    database = datastore "Database" {
      technology "PostgreSQL"
      description "Application data"
    }
    
    cache = datastore "Cache" {
      technology "Redis"
      description "Session cache"
    }
    
    frontend -> backend "REST API"
    backend -> database "SQL"
    backend -> cache "Redis protocol"
  }
  
  user -> frontend "HTTPS"
}
```

## Required Fields

- **Containers**: Must have `technology` and `description`
- **All components**: Must have `description`
- **All strings**: Must use double quotes

## Generation Prompts

### For Single Service (in current repo)

When asked to generate architecture for this service:

```
Generate Sruja architecture DSL for this service:
- Service name: [name]
- Technology stack: [technologies]
- External dependencies: [other services/databases]
- Description: [what this service does]

Requirements:
1. Define all components (containers, datastores) with technology labels
2. Add descriptions to every component
3. Use descriptive relationship labels (include protocol)
4. After generation, I will run `sruja lint` to validate
```

### For Microservices System (multiple repos)

When asked to generate architecture for a microservices system:

```
Generate Sruja architecture DSL for a microservices system.

THIS REPOSITORY contains:
- [Service name]: [description, technologies]

EXTERNAL REPOSITORIES (declare as external systems):
- [Service name]: [description]
- [Service name]: [description]

Requirements:
1. Define ONLY components in THIS repository
2. Declare external services using `external system`
3. Add relationships to external systems
4. Add technology labels to all containers
5. After generation, I will run `sruja lint` to validate
```

## Common Patterns

### API Gateway Pattern
```sruja
system "API Gateway Service" {
  gateway = container "API Gateway" {
    technology "Kong"
    description "API gateway, authentication, rate limiting"
  }
}

user -> gateway "HTTPS"
gateway -> user_service.api "REST"
gateway -> order_service.api "REST"
```

### Event-Driven Pattern
```sruja
system "Order Service" {
  api = container "Order API" {
    technology "Node.js"
    description "Order processing API"
  }
}

system "Inventory Service" {
  worker = container "Inventory Worker" {
    technology "Python"
    description "Processes inventory updates"
  }
}

message_queue = datastore "Message Queue" {
  technology "RabbitMQ"
  description "Event bus for async communication"
}

order_service.api -> message_queue "publishes OrderCreated event"
message_queue -> inventory_service.worker "consumes OrderCreated events"
```

### Database per Service
```sruja
system "User Service" {
  api = container "User API" { 
    technology "Node.js"
    description "User management API"
  }
  db = datastore "User DB" { 
    technology "PostgreSQL"
    description "User data"
  }
  api -> db "SQL"
}

system "Order Service" {
  api = container "Order API" { 
    technology "Python"
    description "Order processing API"
  }
  db = datastore "Order DB" { 
    technology "MySQL"
    description "Order data"
  }
  api -> db "SQL"
}
```

## Best Practices

### Naming
- Use **descriptive names**: "User API" not just "API"
- Use **consistent naming**: "User Service", "Order Service", not "UserService", "order-svc"
- Component IDs are **snake_case**: `user_api`, `order_service`

### Relationships
- Be **specific**: "REST API" not "calls"
- Include **protocol**: "HTTPS", "gRPC", "AMQP"
- Include **direction**: "publishes events to", "reads from"

### Styling
- **2 spaces** indentation
- **Blank lines** between sections
- **Alphabetical order** for relationships when possible

## Validation Rules

The linter will catch:
- **Undefined component references**
- **Missing `technology` on containers**
- **Wrong relationship targets** (must use component ID, e.g. `frontend`, not `frontend.something`)
- **Orphan components** (no relationships)
- **Circular dependencies**
- **Missing descriptions**

## Common Errors

### Error: Undefined reference 'order_api'
**Fix**: Define the component before using it, or declare as external:
```sruja
external system "Order Service" {
  description "Order processing service"
}
```

### Error: Missing 'technology' field on container 'API'
**Fix**: Add technology label:
```sruja
container "API" {
  technology "Node.js"  // Add this
  description "API server"
}
```

### Error: Invalid relationship target 'frontend.web'
**Fix**: Use the component ID directly:
```sruja
// Wrong:
api -> frontend.web "HTTP"

// Correct (if frontend is the ID):
api -> frontend "HTTP"
```
