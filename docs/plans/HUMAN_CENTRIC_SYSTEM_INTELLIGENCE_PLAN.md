# Human-Centric System Intelligence: Practical Plan

**Date:** June 2026
**Status:** Draft
**Trigger:** The assimilation crisis — AI generates code faster than humans can understand it.

---

## The Problem

AI generates code at scale. Humans approve it. But humans can't hold the system in their heads.

This isn't technical debt — it's **codebase cognitive debt**: the gap between what a system does and what any human understands about it. It lives in minds, not in code. A team crippled by cognitive debt hesitates to change things. They treat the system as a fragile black box. They rely on the one senior engineer who knows how it all fits.

This gets worse with multiple repos. No human thinks in repos. They think in systems: *"A user clicks checkout — what happens? Which services? Which teams? What breaks if payments go down?"*

Today that answer lives in a senior engineer's head, a stale Confluence page, or a Slack thread nobody can find.

**Sruja's job: compress that answer from 3 days of asking around into 3 seconds of running a command.**

---

## The Shift: Scan-First, Not DSL-First

Today Sruja asks humans to write `.sruja` files describing their architecture. This creates an adoption barrier: before you get value, you must author and maintain a DSL file. For a single repo this is manageable. For 50 repos across an organization, it's unrealistic.

**The new model:**

| | Old model (DSL-first) | New model (scan-first) |
|---|---|---|
| Architecture source | Human authors `.sruja` files | Scanner discovers from code |
| Human contribution | Everything: structure + intent | Only what scanner can't know: intent, policies, gotchas |
| Value at install | Zero — must author DSL first | Immediate — `sruja scan` gives you a graph |
| Enforcement | Needs full DSL | Works with scan + optional policies |
| Cross-repo | Requires DSL in every repo | Works from scans alone, DSL where available |

**The scanner already finds 80% of the architecture.** Containers, components, services, databases, APIs, dependencies, technologies — all auto-discovered from source code, package manifests, OpenAPI specs, Docker configs, and import analysis.

The `.sruja` file doesn't disappear. It becomes **thinner** — only what requires human judgment:

```sruja
// Auto-generated by sruja init — do not edit structure section
// Edit only: policies, gotchas, constraints, ownership below

PaymentService = container "Payment Service" {
  technology "Rust"          // ← auto-detected
  criticality HIGH           // ← human intent
  owner "@fintech"           // ← human intent

  gotcha "FraudService has no fallback. If it's down, payments fail."
  constraint "Only CartService and WebhookHandler may call PaymentService directly"
  constraint "Must NOT access OrdersDB directly"
}

boundary payments_isolation {
  from PaymentService
  to [OrdersDB]
  allowed false
  reason "Payment must not directly access order data — use OrderService API"
}

decision ADR_012 {
  title "Synchronous fraud check"
  status accepted
  file "docs/adr/012-sync-fraud-check.md"
  affects [PaymentService, FraudService]
}
```

**Adoption path:**
1. `sruja init` → auto-discovers architecture from code (zero human effort, immediate value)
2. `sruja trace`, `sruja explain`, `sruja map` → human gets system understanding
3. Optionally add policies, gotchas, boundaries → enforcement layer activates
4. `sruja drift` → catches when code violates declared policies

Value from day 1. Enforcement when the team is ready. No upfront DSL authoring required.

## Guiding Principles

1. **Zero-friction start.** `sruja init` gives you value. No DSL authoring, no setup wizard, no config files.
2. **Human questions, not graph queries.** "What happens when a user checks out?" not "traverse BFS from node X depth 3."
3. **Compass, not encyclopedia.** ~1,000 tokens of compressed understanding per module (Meta's research: 40% reduction in exploration cost). Never dump raw data.
4. **Situation model, not program model.** Humans easily learn *what* code does. They struggle with *why* it exists. Optimize for the why: decisions, rationale, boundaries, ownership, gotchas.
5. **Scan is truth, DSL is intent.** The scanner discovers reality. The DSL captures intent. Drift between them is the most valuable signal in the system.
6. **Multi-repo is the default.** Single-repo is a special case. Humans think in systems, not repos.
7. **LLM is a premium rendering layer, never a required dependency.** Every feature works without an LLM. LLM calls are opt-in, cost-aware, and always grounded in deterministic facts.

## LLM Cost Strategy

Sruja's value comes from the deterministic graph — the scanner, the traversal engine, the architecture model. An LLM is only needed to *polish* the output into human-friendly narratives. This means LLM costs should be near-zero by default and only incurred when a human explicitly asks for richer output.

### The Cost Hierarchy

```
Free (deterministic, no LLM)           $0.00
  ├─ sruja scan                         tree-sitter + manifests
  ├─ sruja map                          graph layout + ASCII render
  ├─ sruja trace                        graph traversal + template render
  ├─ sruja explain                      template render from graph data
  ├─ sruja before                       blast radius + template render
  ├─ sruja daily                        diff detection + template render
  ├─ sruja cognitive-debt               metric computation (all math)
  └─ sruja drift / lint / classify      deterministic rules

Near-Free (local embeddings, no API)    ~$0.00
  ├─ Entity resolution ("payment")      fastembed BGE-small (local, ONNX)
  ├─ Semantic search                    cosine similarity (local)
  ├─ Cross-repo edge matching           embedding similarity (local)
  └─ Query routing                      heuristic classifier (existing)

Cheap (small model, ~$0.001/call)
  ├─ Entity resolution (fuzzy)          Haiku/Flash for borderline cases
  ├─ Narrative polish (--enrich)         Haiku/Flash for template → prose
  └─ Non-Rust classification            Haiku/Flash for crate tier inference

Moderate (large model, ~$0.01-0.05/call)
  ├─ sruja what-if risk narrative       Sonnet for nuanced risk reasoning
  └─ sruja explain --enrich             Sonnet for rich situation model
```

### Cost Architecture

#### 1. Never Call an LLM by Default

Every command works perfectly with template rendering. The `--enrich` flag (which already exists) is the only trigger for LLM calls. This is already the case today — keep it that way.

| Command | Default (free) | With `--enrich` (LLM) |
|---|---|---|
| `sruja trace "..."` | Template flow diagram | Polished narrative flow |
| `sruja explain X` | Structured template output | Rich human-readable prose |
| `sruja map` | ASCII diagram | Polished system overview |
| `sruja before` | Impact template | Nuanced risk assessment |
| `sruja what-if "..."` | Blast radius + facts | Risk narrative with reasoning |
| `sruja cognitive-debt` | Metric scores + template | Prioritized recommendations |

**Target: 95% of usage is free. 5% uses LLM.**

#### 2. Local Embeddings First, LLM Only for Borderline

Entity resolution (matching "how does payment work" to `PaymentService`) uses a cascade:

```
Step 1: Exact match (free)           "PaymentService" → exact hit
Step 2: Keyword match (free)         "payment" → substring hit
Step 3: Embedding similarity (local) "how does checkout work" → cosine top-k
Step 4: LLM disambiguate (cheap)     "the fraud thing" → Haiku picks from top-3
```

Steps 1-3 cost nothing. Step 4 only fires when the user's query is genuinely ambiguous and the embedding matches multiple candidates with similar scores.

The existing `fastembed` (BGE-small-en-v1.5) is already a dependency. It runs locally via ONNX — no API call, no cost. Wire it into `trace` and `explain` entity resolution (W3.3 in the plan).

#### 3. Prompt Caching for Enrichment

When `--enrich` is used, structure the API call for maximum cache hits:

Sruja already has cache-friendly context (`build_cache_friendly_task_export()` in `logic.rs:1590`). Extend this pattern to enrichment:

```
[Cached prefix — static per repo, ~2K tokens]
  System prompt + grounding instruction
  + repo classification + architecture boundaries
  + element definitions + ownership

[Dynamic suffix — per query, ~500 tokens]
  Specific element data for this query
  + "Produce markdown explaining this element"
```

Anthropic caches at 90% discount. OpenAI at 50%. With a ~2K token cached prefix, a `sruja explain --enrich` call costs:
- Anthropic: $0.003 (cached read) + $0.015 (new output) = **~$0.02**
- OpenAI: $0.005 (cached) + $0.015 (output) = **~$0.02**
- Without caching: ~$0.05

**~60% cost reduction with zero code complexity — just structured prompts.**

Implementation: Extend `enrichment.rs` to send the repo's architecture invariant block as the first message (cached), and the per-element data as the second message (dynamic).

```
File: crates/sruja-cli/src/enrichment.rs (extend, ~50 lines)
```

#### 4. Small Model Routing

Not every enrichment needs Sonnet. Route by task complexity:

| Task | Model | Cost/call | Why |
|---|---|---|---|
| Entity disambiguation | Haiku / Flash | $0.001 | Pick from 3 options — trivial |
| Template → prose polish | Haiku / Flash | $0.002 | Constrained output, grounded facts |
| Risk narrative (what-if) | Sonnet | $0.02 | Needs nuanced reasoning |
| Rich explain narrative | Sonnet | $0.02 | Needs deep comprehension |

Configuration in `.sruja/config.toml`:

```toml
[enrichment]
default_model = "auto"    # auto = route by task
cheap_model = "claude-haiku-4-0-20250514"  # or "gpt-4o-mini"
premium_model = "claude-sonnet-4-20250514"  # or "gpt-4o"
```

When `default_model = "auto"`, Sruja decides. When set to a specific model, all enrichment uses that model. Default: `auto`.

- Narrative generation for all services: batch API
- Ongoing daily use: real-time API (user is waiting)

#### W0.1: `sruja init` Becomes Scan-First

Today `sruja init` sets up an empty `.sruja/` directory and expects humans to write DSL. Change it to:

1. Run `scan_repo()` — discovers containers, services, databases, APIs, dependencies.
2. Generate `.sruja/scan.json` — the auto-discovered architecture graph.
3. Generate a starter `repo.sruja` from the scan — structure section is auto-populated and marked `// auto-generated, do not edit`. Intent section is empty with comments prompting human to add policies, gotchas, ownership.
4. Generate `.sruja/classification.json` from scan (layers, boundaries inferred from crate/module structure).

**Result:** After `sruja init`, you immediately get `sruja map`, `sruja trace`, `sruja explain` working — without writing a single line of DSL.

```

```

#### W0.2: Traversable SystemGraph

The `system.index.json` from federation is a static data structure. Turn it into a traversable graph.

Create `SystemGraph` that wraps the composed system index with traversal methods:

- `neighbors(id, direction)` — follow edges in/out, crossing repo boundaries
- `blast_radius(id, depth)` — transitive impact across repos
- `find_path(a, b)` — shortest path between any two elements in any repo
- `entrypoints()` — external-facing APIs and frontends across all repos
- `data_stores()` — all databases, queues, caches across the system
- `hubs()` — elements with high betweenness centrality (cross-repo choke points)
- `teams()` — group elements by ownership

Support both DSL-derived and scan-derived edges. DSL edges win on confidence.

```
File: crates/sruja-graph/src/system_graph.rs (new ~500 lines)
Extends: sruja-graph-core traits
```

**Validation:** Publish 3 test repos → compose → `system_graph.blast_radius("repoA::Service")` returns elements from all 3 repos.

---

#### W0.3: Cross-Repo Edge Inference

Today `compose()` only merges intra-repo edges. Add a second pass that infers inter-repo relationships — **all deterministic, no LLM needed**:

- **Config matching:** repoA's Docker Compose references `http://cart-service:8080` → match to repoB's `CartService` exposing port 8080. Confidence: HIGH.
- **API matching:** repoA's OpenAPI client references `POST /api/checkout` → match to repoB's OpenAPI server exposing that endpoint. Confidence: HIGH.
- **Name similarity:** repoA imports `@company/cart-service` → repoB is named `cart-service`. Confidence: MEDIUM.
- **Embedding similarity (local):** service names embedded via fastembed → cosine match across repos. Confidence: MEDIUM. Falls back to name similarity.
- **Technology heuristic:** repoA publishes to Kafka topic `payment-events` → repoB subscribes to `payment-events`. Confidence: MEDIUM.

Use the existing `logical_id` and `aliases` fields (already on `SystemIndexNode`, currently unused) for entity resolution. Tag every inferred edge with confidence level. Low-confidence edges appear in output but are clearly marked as `inferred (low confidence)`.

**Cost: $0 — all local computation (string matching + fastembed).**

```
File: crates/sruja-cli/src/commands/federation.rs (extend compose(), ~250 lines new)
File: crates/sruja-export/src/vector.rs (extend for cross-repo matching, ~50 lines)
```

**Validation:** Compose 3 repos where repoA calls repoB's API (via Docker Compose reference) and repoB publishes to Kafka that repoC consumes. Verify both cross-repo edges are inferred.

#### W1.1: `sruja trace` — "What happens when..."

The flagship. Traces a flow across all repos in the system.

```bash
$ sruja trace "user clicks checkout"

── Trace: "user clicks checkout" ──

[frontend]   WebApp → POST /api/checkout
[gateway]    APIGateway → routes to cart-service
[cart]       CartService → SQL READ CartDB
[payments]   PaymentService → gRPC FraudService
[payments]   PaymentService → REST StripeAdapter
[payments]   PaymentService → KAFKA PaymentEvents
[orders]     OrderService ← KAFKA PaymentEvents
[orders]     OrderService → SQL WRITE OrdersDB
[orders]     OrderService → KAFKA OrderCreated

5 repos · 4 teams · 2 topics · 2 databases

⚠ SPOF: FraudService (sync, no fallback)
⚠ SPOF: APIGateway (single entry point)

Decisions: ADR-012 (sync fraud), ADR-008 (Kafka events)
Owners: @checkout-ui @platform @commerce @fintech @risk
```

```bash
$ sruja trace "user clicks checkout" --depth 5    # deeper
$ sruja trace "user clicks checkout" --team @fintech  # my team's involvement
$ sruja trace "user clicks checkout" --json        # machine-readable
```

**How it works:**
1. Resolve query to entry point(s) — cascade: exact match → keyword → local embedding similarity → LLM disambiguate (only if ambiguous). Steps 1-3 are free. Step 4 costs ~$0.001.
2. BFS traversal through `SystemGraph`, following `→` edges. Deterministic. Free.
3. At each hop: resolve repo, load technology/owner/criticality/gotchas. Free.
4. SPOF detection: nodes with high betweenness + single incoming path. Deterministic. Free.
5. Render as compact flow diagram. Template. Free. Keep under 50 lines.

**Cost: $0 by default. ~$0.001 only when entity resolution is ambiguous and requires LLM disambiguation.**

```
File: crates/sruja-cli/src/commands/trace.rs (new ~500 lines)
```

#### W1.2: `sruja explain` — "What is this thing?"

Tells a human *why* something exists, not just what it does. The situation model builder.

```bash
$ sruja explain PaymentService

── PaymentService ──
  repo: payments  |  team: @fintech  |  criticality: HIGH

What it does:
  Initiates payment transactions for the checkout flow.
  Calls FraudService synchronously for risk assessment.
  Processes charges via StripeAdapter.
  Publishes payment events to Kafka.

Where it fits:
  ← CartService (cart repo) sends checkout requests
  ← WebhookHandler (payments repo) receives Stripe callbacks
  → FraudService (fraud repo) for risk checks
  → StripeAdapter (payments repo) for charges
  → Kafka PaymentEvents → OrderService, 3 other consumers

What to know before changing it:
  ⚠ FraudService has no fallback — if it's down, payments fail
  ⚠ PaymentEvents is v2 schema — v1 consumers removed 2025-Q1
  ⚠ Stripe webhook handler is in a separate module
  🔒 Only CartService and WebhookHandler may call it directly
  🔒 Must NOT access OrdersDB directly

  OrderService (orders repo) — HIGH risk
```

4. Gotchas and boundaries come from DSL intent layer if present, otherwise inferred (undocumented high-centrality nodes = implicit gotcha). Free.
5. Keep under 40 lines. Compass, not encyclopedia.
6. `--enrich` flag: send structured facts to LLM for prose polish. Costs ~$0.01-0.02. Optional.

**Cost: $0 by default. ~$0.02 with `--enrich`.**

#### W3.1: Cognitive Debt Score

A single number that answers: "How well does this team understand their system?"

**Entirely deterministic. No LLM needed.** All metrics are computed from the graph + git data:

```bash
$ sruja cognitive-debt

HIGH RISK:
  PaymentService (payments repo)
    8 downstream consumers · 4 repos · 2 undocumented deps · 0 recent ADRs
    Bus factor: 1 (@jane authored 73% of changes)
    → If @jane leaves or PaymentService breaks, 4 teams are blocked.
    → Run: sruja explain PaymentService

MEDIUM RISK:
  APIGateway (infra repo)
    Hub node (12 edges) · no gotchas documented · no runbook
    → Critical choke point with no operational knowledge captured.

LOW RISK:
  CartService (cart repo)
    2 consumers · well-documented · 3 ADRs · team of 4

System score: 62/100 (needs attention)
Threshold: 70 (your CI gate)
```

**Metrics per element:**
- **Undocumented blast radius**: downstream consumers not in any DSL/policy × criticality
- **ADR staleness**: months since last ADR affecting this element
- **Bus factor**: % of changes by single author
- **Hub without docs**: high betweenness × zero gotchas/runbooks
- **Cross-repo coupling**: number of repos depending on this element

#### W3.2: Grounded Narratives (Cost-Optimized)

The `--enrich` flag exists. Make it work properly and cheaply:

**Two-tier approach:**
- **Default (free):** Template rendering from structured facts. Every `explain`, `trace`, `map` works perfectly without LLM. Templates are deterministic, fast, and produce structured human-readable output.
- **`--enrich` (paid):** Send structured facts to LLM for prose polish. Uses small model routing and prompt caching to minimize cost.

**Cost optimization for `--enrich`:**
1. **Prompt caching:** Send repo architecture as cached prefix (~2K tokens cached, ~60% cost reduction). Extend the existing `build_cache_friendly_task_export()` pattern.
2. **Small model routing:** Entity disambiguation and template → prose use Haiku/Flash (~$0.002/call). Only risk narratives use Sonnet (~$0.02/call). New `auto` routing mode in `.sruja/config.toml`.
3. **Strict grounding:** *"Only use the provided data. Do not infer, fabricate, or add information not present in the input."* Keeps output short (fewer output tokens = lower cost) and accurate.
4. **Token budget enforcement:** Max 1,000 output tokens per enrichment call. Enforced by the existing `TokenBudget` system.

**Key invariant: if the narrative contradicts the graph, the graph wins.**

```
File: crates/sruja-cli/src/narrative.rs (new ~250 lines)
File: crates/sruja-cli/src/enrichment.rs (extend, ~100 lines — caching + routing)
```

**Cost: $0 default. $0.002–0.02 with `--enrich` depending on task and model routing.**

#### W3.3: Semantic Entity Resolution (Local, Free)

Wire the existing `vector.rs` embedding module so `trace` and `explain` find things by description — **all local, no API call**:

- Index all nodes from scan graph (labels, descriptions, technologies) using fastembed BGE-small-en-v1.5 (already a dependency, runs via ONNX on CPU).
- `sruja trace "how does payment work"` → matches PaymentService even if the user didn't use the exact name.
- `sruja explain "the thing that calls stripe"` → resolves to StripeAdapter.
- Entity resolution cascade: exact match (free) → keyword (free) → embedding cosine top-3 (free, local) → LLM disambiguate ($0.001, only if 2+ candidates score within 5%).

**Cost: $0 for 95%+ of queries. ~$0.001 when truly ambiguous.**

#### W3.4: `sruja what-if` — Safe Change Modeling

Before making a change, simulate the impact:

**Two-tier output:**
- **Default (free):** Deterministic blast radius analysis. Graph mutation + template rendering. Shows direct effect, blast radius (repos/teams/topics/databases), and affected decisions. All from graph traversal.
- **`--enrich` (paid):** LLM adds risk reasoning — why something is HIGH risk, what the implications are. Uses Sonnet for nuanced reasoning (~$0.02).

```bash
$ sruja what-if "remove FraudService sync check"

── What-If ──

Direct effect:

Decisions to update: ADR-012 (sync fraud check) → supersede

Next steps:
  1. Write ADR for async fraud before coding
  2. Run: sruja explain FraudService
  3. Notify @fintech @risk
```

## What We're NOT Building

- **An autonomous coding agent.** Sruja helps humans understand, not write.
- **An IDE-only tool.** CLI-first. Terminal is universal.
- **A monitoring platform.** That's Datadog. Sruja works with static code.
- **A documentation generator.** Sruja generates comprehension, not docs. Docs are a side effect of `--persist`.
- **An AI chatbot.** Sruja is a deterministic engine. AI is optional enrichment.

## Risks

| Risk | Mitigation |
|---|---|
| Scan quality varies by language | Tree-sitter supports 13 languages; confidence scoring flags low-quality discoveries |
| Cross-repo edges might be wrong | Confidence levels on every inferred edge; low-confidence clearly marked |
| LLM hallucinates in narratives | Strict grounding — narrative is a rendering of facts, never a source. Fallback to templates. |
| LLM costs spiral | Every feature works without LLM. `--enrich` is opt-in. Prompt caching + small model routing. `sruja costs` makes spending visible. |
| Nobody uses comprehension tools | Lead with `sruja trace` — answers the #1 question: "what happens when..." |
| Terminal UI is niche | CLI is the universal interface. Web explorer and VS Code for those who prefer GUI. |
| Adoption friction | `sruja init` is zero-config. No DSL required. Value from second 1. No LLM key needed. |

**Sruja is the comprehension engine that lets any human understand any system — by auto-discovering architecture from code and answering human questions across repos, teams, and services. It costs nothing to run and uses AI only when you want richer output.**
