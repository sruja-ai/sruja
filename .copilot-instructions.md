# GitHub Copilot – Sruja DSL

When working with Sruja architecture DSL (`.sruja` files):

## File context

- **Extension:** `.sruja`
- **Validate:** `sruja lint file.sruja`
- **Export:** `sruja export json|markdown|mermaid|svg`

## Structure

1. Start with `architecture "[name]"` block.
2. Define components (person, system, container, datastore) before using them in relationships.
3. Nest: systems inside architecture, containers/datastores inside systems.
4. Relationships after definitions: `source -> target "label"`.

## Component definitions

```sruja
user = person "User" {
  description "End user who interacts with the system"
}

system "Application" {
  frontend = container "Web Frontend" {
    technology "React"
    description "User interface"
  }
  backend = container "Backend" {
    technology "Node.js"
    description "API server"
  }
  database = datastore "Database" {
    technology "PostgreSQL"
    description "Data persistence"
  }
}
```

## Relationships

- Syntax: `source -> target "label"`.
- Use descriptive labels: "HTTPS", "REST API", "publishes events to".
- Only reference defined component IDs (e.g. `frontend`, `backend`, not `frontend.web`).

## Required fields

- **Containers:** `technology` and `description`.
- **All components:** `description`; all strings in double quotes.

## Example

```sruja
architecture "Simple Web App" {
  user = person "User" {
    description "End user"
  }

  system "Web App" {
    frontend = container "Frontend" {
      technology "React"
      description "User interface"
    }
    backend = container "Backend" {
      technology "Node.js"
      description "API server"
    }
    database = datastore "Database" {
      technology "PostgreSQL"
      description "Data persistence"
    }
  }

  user -> frontend "HTTPS"
  frontend -> backend "REST API"
  backend -> database "SQL"
}
```

## Best practices

1. Define every component before use.
2. Use descriptive names and relationship labels.
3. Run `sruja lint` after changes.

## Common errors

- Undefined component references.
- Missing `technology` on containers.
- Wrong relationship target (use component id, e.g. `frontend`, not `frontend.something`).
- Orphan components; circular dependencies.
