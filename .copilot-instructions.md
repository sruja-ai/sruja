# GitHub Copilot – Sruja DSL

When working with Sruja architecture DSL (`.sruja` files):

## File context

- **Extension:** `.sruja`
- **Validate:** `sruja lint file.sruja`
- **Export:** `sruja export json|markdown|mermaid|svg`

## Structure

Use **flat, top-level declarations**. The legacy `architecture "Name" { }` wrapper is not part of the DSL.

1. Define components (person, system, container, database, queue) at the top level before using them in relationships.
2. Nest containers/datastores inside systems when they belong to that system.
3. Relationships after definitions: `source -> target "label"`. Use PascalCase for element IDs.

## Component definitions

```sruja
User = person "User" {
  description "End user who interacts with the system"
}

WebApp = system "Web App" {
  Frontend = container "Frontend" {
    technology "React"
    description "User interface"
  }
  Backend = container "Backend" {
    technology "Node.js"
    description "API server"
  }
  Database = database "Database" {
    technology "PostgreSQL"
    description "Data persistence"
  }
}
```

## Relationships

- Syntax: `source -> target "label"`.
- Use descriptive labels: "HTTPS", "REST API", "publishes events to".
- Reference component IDs (e.g. `WebApp.Frontend`, `WebApp.Backend` for nested; top-level by ID).

## Required fields

- **Containers:** `technology` and `description`.
- **All components:** `description`; all strings in double quotes.

## Example

```sruja
User = person "User" {
  description "End user"
}

WebApp = system "Web App" {
  Frontend = container "Frontend" {
    technology "React"
    description "User interface"
  }
  Backend = container "Backend" {
    technology "Node.js"
    description "API server"
  }
  Database = database "Database" {
    technology "PostgreSQL"
    description "Data persistence"
  }
}

User -> WebApp.Frontend "HTTPS"
WebApp.Frontend -> WebApp.Backend "REST API"
WebApp.Backend -> WebApp.Database "SQL"
```

## Best practices

1. Define every component before use.
2. Use descriptive names and relationship labels.
3. Run `sruja lint` after changes.

## Common errors

- Undefined component references.
- Missing `technology` on containers.
- Wrong relationship target (use component ID; for nested use e.g. `WebApp.Frontend`).
- Orphan components; circular dependencies.
