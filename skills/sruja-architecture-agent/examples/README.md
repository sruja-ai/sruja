# Sruja Architecture Agent Examples

This directory contains example architectures generated by the Sruja Architecture Agent skill. These examples demonstrate different use cases and patterns for architecture discovery.

## Examples Overview

### 01-simple-web-service

**Scenario:** Single Node.js API with PostgreSQL database

**What it demonstrates:**
- Basic architecture discovery from a codebase
- Single system with one container and one datastore
- Technology detection (Node.js, Express, PostgreSQL)
- Endpoint discovery from route files
- Personas (API clients)

**Files:**
- `user-api.sruja` - Complete architecture for a user management API

**Key features:**
- Metadata includes framework version and repository info
- Endpoints detected from code analysis
- Database connection details from configuration

---

### 02-microservices-platform

**Scenario:** E-commerce platform with three microservices

**What it demonstrates:**
- Multi-service architecture discovery
- Service decomposition and boundaries
- Cross-service relationships
- Import/export pattern for modular architectures
- External system integration (Stripe)
- Multiple personas (Shopper)

**Files:**
- `architecture.sruja` - **Main working example** (consolidated architecture with all services)
- `user-service.sruja` - Reference file showing User Service in isolation
- `order-service.sruja` - Reference file showing Order Service in isolation
- `payment-service.sruja` - Reference file showing Payment Service in isolation

**Key features:**
- Consolidated architecture file defines all three services together
- Demonstrates cross-service communication (REST, gRPC)
- Shows external dependencies (Stripe) and end users (Shopper persona)
- Each service uses different technology stacks (Node.js, Python, Go)
- Includes event-driven architecture with message queues (RabbitMQ)

**Note:** The individual service files (`user-service.sruja`, etc.) are provided as reference examples showing what each service looks like in isolation. In a real distributed setup, each service would maintain its own architecture file with external system references to other services (see the `multi-repo` pattern in the main examples directory).

---

### 03-documentation-based

**Scenario:** Content platform derived from documentation

**What it demonstrates:**
- Architecture discovery from documentation instead of code
- Useful when code access is limited
- Captures architecture intent from design docs
- Multiple user personas (Content Editor, Content Reader)
- External authentication service (Auth0)

**Files:**
- `content-platform.sruja` - Architecture derived from docs

**Key features:**
- Metadata indicates source is "documentation"
- Comments reference where information came from
- Includes CDN/infrastructure details from deployment docs
- Rich persona definitions with behaviors and segments

## How to Use These Examples

### Learning the Pattern

1. **Start simple** - Review `01-simple-web-service` to understand basic structure
2. **Scale up** - Study `02-microservices-platform` for complex systems
3. **Alternative sources** - Check `03-documentation-based` for doc-driven discovery

### Testing the Agent

Use these examples to test if your AI assistant correctly follows the skill:

```
"Analyze my repository similar to example 01-simple-web-service"

"Generate an architecture like 02-microservices-platform for my services"

"Create documentation-based architecture like example 03"
```

### Validating Output

After the agent generates architecture:

```bash
# Validate each file
sruja lint user-service.sruja

# Validate consolidated architecture
sruja lint architecture.sruja

# Export to different formats
sruja export architecture.sruja --format mermaid
sruja export architecture.sruja --format markdown
```

**Note about warnings:** You may see warnings like "Element X is defined but not referenced by any relation" for top-level systems. These warnings are acceptable when the system's internal components (containers, datastores) are referenced in relationships. For example, if `user_service.api` is referenced but `user_service` itself shows a warning, that's expected behavior.

## Common Patterns

### Single Service Pattern
```
system "Service Name" {
  container + datastore + relationships
}
person "User" { ... }
user -> service
```

### Microservices Pattern (Consolidated)
```
// architecture.sruja - All services in one file
service_a = system "Service A" {
  api = container "API" { technology "Node.js" }
  db = datastore "Database" { technology "PostgreSQL" }
  api -> db "SQL"
}

service_b = system "Service B" {
  api = container "API" { technology "Python" }
  db = datastore "Database" { technology "MongoDB" }
  api -> db "MongoDB protocol"
}

// Cross-service relationships
service_a.api -> service_b.api "REST API"
```

**Note:** Import functionality is planned but not yet implemented. For multi-repo setups, see `book/valid-examples/` for canonical patterns, and model multi-repo boundaries using `external_system` references.

### Documentation Pattern
```
system "System" {
  metadata {
    source "documentation"
  }
  // Comments indicating doc sources
}
```

## What Gets Detected

### From Code Analysis
- Languages and frameworks
- Entry points and ports
- Database connections
- External API clients
- Message queues and event streams
- Configuration and environment variables

### From Documentation
- System descriptions
- Deployment patterns
- User personas
- Business context
- SLAs and requirements

## Best Practices

1. **Start with simple examples** before tackling complex microservices
2. **Use imports** for multi-file architectures to keep them manageable
3. **Add metadata** to capture important details (ports, versions, URLs)
4. **Define personas** to understand who uses your system
5. **Document sources** when using documentation-based analysis
6. **Validate frequently** with `sruja lint` as you iterate
